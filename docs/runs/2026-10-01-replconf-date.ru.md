пройдены на HQbird 2.5.9 и 3.0.15: 2.5.9 — 36/36, 3.0.15 — 36/36. Прогон опроверг сравнение
дат «по полям» у плагина, который ставит HQbird, и нашёл настоящую причину

## 4. Находки и правки узла

### 4.1. Плагин HQbird на Linux и причина V-12

Плагин, который ставит HQbird 2.5.9 и 3.0.15 (до 2.1.0, md5 `5c0e9f55…`,
читает v1.2 и v2.0), проверен матрицей файлов на реплике обоих стендов,
1 октября:

| Файл | Attach |
|---|---|
| v2.0, `2099-12-29` | работает |
| v2.0, `2028-01-31` (DataGuard без баз) | работает |
| v2.0, `2026-10-01` (сегодня) | отказ, «Valid date is expired!» |
| v1.2, любой срок, любой заполнитель; образцы DataGuard; шаблон HQbird | отказ, «Valid date is expired!» |
| плагин 2.1.0 и любой из этих файлов v2.0 / файл узла | работает |

- Дата сравнивается целиком, как у 2.1.0. Правила «по полям» из исходников
  `replconf-master` у этой сборки нет: 30-е и 31-е число ни при чём.
- **v1.2 эта сборка не читает.** HQbird ставит шаблон
  `/opt/hqbird/conf/replconf.hqbird.empty` в v1.2. Первый старт Firebird при
  установке читает его и падает (на всех 4 хостах 1 октября). Потом
  DataGuard пишет свой файл в v2.0 (`2028-01-31`), и следующий старт
  проходит. Это и есть V-12.
- Узел считал этот плагин «по полям». Правка: v1.2 при таком плагине —
  поломка, дата — целиком.

### 4.2. Автоактивация на мастере

- Юнит узла `Wants=` Firebird: старт узла поднимает Firebird. HQbird 3.0 на
  сломанном файле тут же падает, а проверка при старте узла видит его
  работающим. Правка: пока движок сломан и рестарт нельзя, проверка каждую
  минуту, до 15 раз.
- fbagent отдаёт состояние своей последней операции. Firebird, упавший сам
  после рестарта через fbagent, для него остаётся `running`. Правка: узел
  считает Firebird остановленным и тогда, когда порт дважды не отвечает.
- HQbird 2.5 под fbguard на сломанном файле поднимает сервер после каждого
  отказа. Мастер остаётся с `critical` или переключается, если узел застал
  порт закрытым. Оба исхода тест принимает.

### 4.3. Прочее

- HQbird 2.5 тоже отказывает в attach по истёкшей дате, как 3.0.
- Свежая реплика сама активировала свой файл при первом старте узла (файл
  DataGuard ей казался сломанным по старой модели; теперь он не сломан, но
  шаблон v1.2 — сломан).
- Пока в `node.json` прошедшая дата, `GET /v1/replconf` не отдаёт
  `valid_till`, хотя файл на диске со старой датой работает. Не исправлено.
- Ошибки теста первого прогона (исправлены): проверка алерта без
  `GET /v1/replconf`, текст алерта, дата из API вместо файла, ожидания по
  старой модели плагина.

## 5. Не проверено

- Связка goafts → fbagent → `node.json`: стенд пишет дату в `node.json` при
  остановленном узле, как fbagent. Сторону fbagent покрывают его юнит-тесты.
- Windows-хосты.

## 6. Стенды после прогона

g25 и g30 работают; удалить, когда не нужны (`do destroy`).
