## 5. Найденные проблемы (RCM)

1. **Блок нового мастера показывает чужие реплики.** После promote у старого
   и нового мастера один GUID, RCM кладёт их в одну группу, и блок нового
   мастера (companion) показывает Ghost replica1 и живую replica2 — реплики
   старого мастера. Так же работает m2 в выпущенной версии.
2. **Clear возвращает ORPHANED-запись донора.** После «Clear» Ghost-строка
   уходит, но запись донора (ORPHANED, она остаётся на узле после promote)
   снова появляется строкой «Error» под старым мастером. Убрать её нечем:
   см. п. 3.
3. **«Remove from management» для реплики с файлом на диске.** Узел не
   забывает запись реплики, пока есть файл и её `.Incoming`
   (`mailbox_active`, правило F-8), а RCM к этому моменту уже добавил файл в
   `exclude_paths`. Итог: запись ORPHANED и исключена. В RCM написано, что
   файлы остаются на диске — для реплик это не работает. Тесты `rcmtable`
   поэтому сначала удаляют файл. Найдено на отладочном стенде.

## 6. Как повторить

```bash
python tb.py --config config/<do config with replica1.companion> test rcmtable
python tb.py --config config/<do config with replica1.companion> test promote
```

Порядок полного прогона: engineparams, basic, reinit_cycles --cycles 3,
datacheck, disasters, states, gaps, rcmtable, promote (оставляет db2
перенесённой), upgrade (сбрасывает состояние узлов), затем очистка.
