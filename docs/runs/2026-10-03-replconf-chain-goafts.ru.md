# Цепочка goafts → fbagent → node.json тестом test bed: прогон 2026-10-03

Итог: **сценарии T1–T5 теперь проверяются одной командой**, тестом
`replconfchain` на стенде, который собирает goafts (`tb.py goafts up`). На
пути клиента (установщик fbagent, HQbird без плагина replconf) прошло всё:
HQbird 3.0 — 24 из 24, HQbird 2.5 — 28 из 28 (T4 — после правки проверки,
разд. 4). Прогон нашёл ошибку fbagent на полном HQbird (симлинки плагина),
она исправлена (fbagent `0c8e07e`, к выпуску 2.59.1). Одна находка открыта:
старый fbagent в кластере goafts портит `node.json`, а узел не говорит
«обновите fbagent» (разд. 4).

Планы: hqcluster-node `docs/next-steps-after-2027.4.3-plan.md` (Н8 п. 1–2),
`docs/release-replconf-2027.4.3-plan.md` (Ш6, Ш7 п. 2).

## 1. Что появилось в test bed

- `tb.py goafts up|status|date|channel|down` (`tblib/goafts.py`): агенты
  ставятся из goafts и регистрируются (CSR одобряет test bed), goafts
  включает хосты в один кластер (managed PKI, участники из конфига), каждый
  агент сам пишет `node.json` / `rcm.json` и ставит узел и RCM из своего
  канала. Дальше тесты test bed работают как обычно: API узла вызывается на
  хосте с его собственными сертификатами.
- Два способа поставить агента: на HQbird, уже поставленный `hosts prepare`
  (полный установщик HQbird), или установщиком fbagent
  (`goafts.installer_dir`: `fbagent-fbXX_known.sh --goafts chess1 --enroll
  --cluster`) на пустой хост — так ставит клиент.
- Админка goafts через p5ctl fbagent (`goafts.admin.p5ctl`): в конфиге test
  bed нет секретов goafts.
- Модуль `20-goafts`: `installer`, `cluster-prep` (папки кластера, корень
  баз, пароль SYSDBA агента), `channel` (канал узла и RCM, самообновление
  агента), `agent-swap` (другая сборка fbagent на месте установленной).
- Тест `replconfchain` (`docs/tests.md`): t1 установка, t3 дата, t5 закрытый
  корень, t4 старый агент (`--old-fbagent`), t2 обновление (`--to-channel`).
- CSR fbagent 2.5x называется по id агента (`<имя хоста>ГГММДД`), а не по
  имени хоста: test bed принимает и такое имя (только имя и шесть цифр).

Подробно:

- **t1, путь клиента.** Установщик fbagent ставит HQbird без плагина и без
  `replconf.properties`. После `goafts up` агент записал `node.json` из
  кластера (id участника, дата 2027-03-31) и поставил узел и RCM 2027.4.5;
  узел сам включил replconf через fbagent (`not_set_up`, решение Р2): плагин
  2.1.0 и `replconf.properties` — `root:root 644`, `plugins/` и `bin/` —
  `root:root 755`. RCM работает; база реплицируется, строки совпали.
- **t1, полный HQbird.** Установщик HQbird делает `plugins/libreplconf.so` и
  `bin/replconf.properties` симлинками в `/opt/hqbird` (файлы пользователя
  firebird, плагин 666). Узел такую настройку сам не трогает — ждёт
  оператора (верно). Активация оператором (`POST /v1/replconf/activate`)
  падала: помощник fbagent `replconf-install` отвечал «is not a regular
  file». Исправлено в fbagent `0c8e07e`: симлинк root заменяется файлом
  root, через симлинк ничего не пишется и не читается, сам симлинк остаётся
  копией `.hqcluster-<время>`. С 2.59.1-lab.1 активация прошла через fbagent
  (`via: fbagent`, плагин 2.1.0). Строки FAIL «the node leaves it» в прогоне
  `ga` — от прошлой неудачной попытки: узел держит `activate_error`, пока
  активация не пройдёт; проверка поправлена (ошибка в заметке, не провал).
- **t3.** Дата кластера 2027-03-31 → 2027-06-30 дошла до `node.json` обоих
  узлов за 51–52 с, файл узла получил дату, PID Firebird не изменился. Дата
  убрана из кластера — `node.json` не тронут. Вчерашняя дата не записана,
  агент пишет «has already passed; node.json keeps its date». Дата
  возвращена.
- **t5.** Узел остановлен, его файл удалён, корень Firebird `root:root 755`,
  узел запущен. fbagent 2.59.0 сам открыл корень через 2 мин (`chgrp
  firebird; chmod g+w,+t`), узел записал файл, replconf активен (Н9 п. 1
  теперь проверен на стенде).
- **t4.** fbagent 2.56.0 на реплике 2.5, самообновление выключено, плагин и
  `replconf.properties` убраны. В кластере goafts старый агент сам переписал
  `node.json`: `firebird.replication_conf = /opt/firebird/replication.conf`
  (с 2.57.0 агент такое значение убирает). Узел ответил `not_replconf` и
  поднял `config_backend_mismatch` (warn): «Firebird 2.5 reads a replconf
  file, but firebird.replication_conf is …replication.conf: what the node
  writes has no effect». В `plugins/` и `bin/` ничего не записано; с
  возвращённым агентом `node.json` исправлен, узел снова включил replconf.
  Проверка t4 сначала ждала только `activate_error fbagent_outdated`
  (ветка узла, чей `node.json` агент не трогает); теперь принимает обе
  формы отказа и пишет, какая сработала. Повтор t4 на gi25 и ga25 — 4/4.
  На ga25 первый прогон ещё дал FAIL «nothing is written»: проверка
  сравнивала вывод `ls -la`, где есть время изменения `..` (корня Firebird,
  куда узел пишет свой файл). Теперь сравниваются имя, владелец, права,
  размер и цель ссылки каждого файла в `plugins/` и `bin/`.
- **ga30 24/26, ga25 26/30.** Все FAIL — проверки теста, не продукта: две
  строки «the node leaves it» на стенд (ошибка активации до исправления
  fbagent) и на ga25 две строки t4 (старая проверка отказа и `ls -la`).
- **t2.** Канал узла и RCM переведён на `ops-test`: агенты обновили узлы и
  RCM 2027.4.5 → 2027.4.5.1 за секунды (проверка при перезапуске агента),
  replconf активен, строки совпали после нагрузки.

## 5. Находки

- **Исправлено — fbagent: replconf на полном HQbird.** Без исправления узел
  не мог включить replconf через fbagent ни сам, ни по запросу оператора на
  любой установке HQbird с DataGuard (симлинки плагина). fbagent
  `0c8e07e`, юнит-тесты помощника под root (лаба) и стенды `ga`.
- **Открыто — узел: старый fbagent в кластере goafts.** Агент до 2.57.0
  пишет в `node.json` участника `replication_conf = <root>/replication.conf`;
  на HQbird 2.5/3.0 узел поднимает только `config_backend_mismatch` (warn) и
  советует оставить поле пустым — но `node.json` пишет агент, оператор его
  не исправит. Предложение: в таком случае (узел под управлением кластера)
  называть причину — «обновите fbagent до 2.57.0+» — и поднимать алерт выше
  warn: репликация хоста не работает.

## 6. Не проверено

- t4 в ветке `activate_error fbagent_outdated` (агент без маршрута, но
  `node.json` не испорчен) — только юнит-тестами узла: в кластере goafts
  старый агент всегда переписывает `node.json`.
- T1 на HQbird 5.0 через goafts (в матрице 2027.4.3 — «как раньше»): тест
  проверяет только, что узел отвечает; стенд 5.0 не поднимался.
