# Полный прогон стенда на DigitalOcean, 2026-09-27

Итог: 94 проверки из 96 прошли. Упал только тест `datacheck` (2 проверки):
мастер не смог забрать замеры реплик из-за ошибки проверки TLS-сертификата.
Ошибка найдена и исправлена в узле и в стенде, но повторный прогон ещё не
делался.

## 1. Что проверялось

Сборка hqcluster-node с исправлениями из плана улучшений:

- **N-12** — одна запись в реестре реплики на один файл базы (раньше скан и
  реинициализация оставляли две записи с разными id);
- **N-11** — реплика, которая ждёт пропущенный сегмент, имеет состояние
  `LAGGING` с причиной `blocked_on_segment`;
- **N-10** — id алерта `replication_paused_reinit_scheduled` содержит реплику
  и поколение;
- **N-09** — периодическая проверка данных (число строк и значение генератора
  на мастере и репликах, история за 7 суток, сравнение на мастере);
- **N-14** — после реинициализации в control file реплики не остаётся
  активных транзакций.

Узел собран до исправления TLS (коммит `88642aa` в hqcluster-node).

## 3. Как работает прогон

Прогон — это bash-скрипт на машине оператора. Он вызывает `tb.py` по шагам.
Дроплеты удаляются в конце всегда, даже если шаг упал: очистка стоит в
`trap ... EXIT`.

| Шаг | Команда | Что делает |
|---|---|---|
| 1 | `do create` | создаёт 3 дроплета |
| 2 | `hosts prepare --hosts all` | ставит Firebird и нужные пакеты |
| 3 | `check` | проверяет конфиг, ssh и Firebird на хостах |
| 4 | `install --source local` | ставит fbagent, узел, RCM из локальных копий; выпускает сертификаты |
| 5 | `dbs prepare --count 2` | создаёт базы на мастере и первую копию на репликах |
| 6 | `loadgen deploy --from local` | копирует генератор нагрузки на мастер |
| 7 | `test basic`, `reinit_cycles --cycles 3`, `datacheck`, `disasters` | тесты (раздел 4) |
| 8 | `dbs remove`, `uninstall`, `hosts wipe`, `do destroy`, `do list` | очистка; `do list` должен быть пустым |

## 4. Как работают тесты

### Проверка «converge»

Её вызывает каждый тест после остановки нагрузки. В этом прогоне в ней было
три проверки:

1. **Строки.** Число строк во всех таблицах с ключом на каждой реплике равно
   числу на мастере. Ожидание до 900 с, повтор каждые 20 с.
2. **Control file реплики.** В файле `{GUID}` в папке журналов реплики за 90 с
   не остаётся активных транзакций (N-14).
3. **Записи реплики.** В `GET /v1/databases` на каждой реплике одна запись на
   файл базы (N-12).

Четвёртую проверку добавили после этого прогона. Мастер должен видеть в своём
журнале передачи (`GET /v1/transfer`), что `last_applied` каждой реплики дошёл
до `last_acked`.

### basic

Нагрузка 3 минуты, остановка, converge по каждой базе.

### reinit_cycles

Три цикла реинициализаций под нагрузкой: `standard`, `smooth`, `standard`.
Каждая база переинициализируется на каждой реплике. Для каждой
реинициализации проверяется:

- операция завершилась успешно;
- на мастере не остался файл `<db>.delta` (блокировка nbackup снята);
- поколение базы на реплике выросло.

В конце: converge по каждой базе.

### datacheck

1. Через `PUT /v1/config` на всех узлах включается проверка данных:
   интервал 60 с, ожидание тишины 30 с, таймаут запроса 120 с. Список таблиц —
   все таблицы с ключом. Узлы перезапускаются.
2. Нагрузка 4 минуты, остановка, converge.
3. Проверки по каждой базе:
   - на каждом узле есть история (`GET /v1/databases/{db_id}/datacheck`)
     хотя бы с одним замером `ok`;
   - среди сравнений на мастере нет `mismatch`: пара, снятая под нагрузкой,
     должна быть `not_comparable`;
   - за 600 с для каждой реплики появляется `match`;
   - на мастере нет алерта `data_mismatch`.
4. Проверка выключается, узлы перезапускаются.

### disasters

Семь сценариев, каждый под нагрузкой. После каждого сценария — converge.

| Сценарий | Что происходит |
|---|---|
| `replica-node-stop` | служба узла на реплике остановлена |
| `replica-node-kill` | процесс узла на реплике убит; служба должна его перезапустить |
| `master-node-stop` | служба узла на мастере остановлена |
| `both-nodes-stop` | обе службы остановлены |
| `replica-fb-stop` | Firebird на реплике остановлен; мастер должен показать `last_acked > last_applied` |
| `master-fb-restart` | Firebird на мастере перезапущен через API узла |
| `partition` | реплика закрывает порт узла от мастера правилом firewall |

## 6. Анализ

### Что подтверждено

- **N-12.** Проверка «одна запись на файл» прошла во всех 13 converge. Это
  проверено после 12 реинициализаций, после перезапусков узлов и после
  разрыва сети. Раньше порядок «скан, потом реинициализация» оставлял вторую
  запись.
- **N-14.** Ни в одном converge в control file реплики не осталось активных
  транзакций.
- **Реинициализация.** Все 12 прошли, включая режим `smooth`. Файлов `.delta`
  на мастере не осталось, поколение каждый раз росло.
- **Аварии.** Все 7 сценариев прошли. Реплики догоняют мастер после
  остановок, убийства процесса, перезапуска Firebird и разрыва сети.
- **N-09, часть «замеры».** Каждый узел вёл свою историю. Все замеры
  (от 4 до 15 на узел и базу) имели статус `ok`.
- **N-09, правило «не сравнимо — не ошибка».** Все 54 сравнения получили
  `not_comparable`. Ложных `mismatch` и алертов `data_mismatch` не было.

### Почему упал datacheck

Мастер не получил ни одного замера реплики. Каждый запрос
`GET /v1/peer/datacheck/{db_id}` заканчивался ошибкой x509. Поэтому все
сравнения стали `not_comparable`, и `match` не появился ни для одной реплики.

Причина — в узле. Каналы передачи сегментов (A и B) проверяют сертификат
реплики по имени из `PeerServerName`: `localhost` или node_id. Опрос
подтверждений (peerpoll), `verify` и datacheck проверяли сертификат по хосту
из URL реплики, то есть по IP-адресу.

На стенде это проявилось так. Сертификаты остались от прошлых дроплетов.
В их SAN были старые внутренние адреса. Новые дроплеты получили другие
адреса. Передача сегментов работала, а все запросы по URL падали.

### Скрытое следствие

Опрос подтверждений тоже падал. Поэтому `last_applied` в журнале передачи на
мастере не двигался: он остался на 83 и 87, хотя подтверждено было 114–116
сегментов. Реплики при этом применяли сегменты: строки совпадали.

Два вывода:

- проверка сценария `replica-fb-stop` («acked больше applied, пока Firebird
  реплики остановлен») в этом прогоне прошла бы в любом случае. Она ничего не
  доказала;
- проверки converge этого не заметили. Для этого добавлена четвёртая
  проверка (раздел 4).

### Исправления

| Где | Что |
|---|---|
| hqcluster-node `88642aa` | peerpoll, verify и datacheck проверяют сертификат реплики по `PeerServerName`, как каналы A и B; тест `TestAcksCheckTheShippersServerName` |
| стенд, `tblib/cluster.py` | `ensure_certs` выпускает новые сертификаты, если изменились узлы или их адреса (`state/certs/made-for.json`) |
| стенд, `tests/_common.py` | четвёртая проверка converge: `last_applied` каждой реплики доходит до `last_acked` за 120 с |

### Мелочь

`hosts wipe` печатает `products.sh: line 132: /proc/<pid>/cmdline: No such
file or directory`. Процесс завершился между перебором `/proc` и чтением
файла. Перенаправление `2>/dev/null` стоит после `<"$p/cmdline"`, поэтому
ошибку открытия файла печатает сама оболочка. На результат это не влияет:
`leftovers` пуст.

## 7. Что осталось

Повторить прогон с узлом, собранным из `88642aa` или новее. Ожидается:

- `match` для каждой реплики в `datacheck`;
- четвёртая проверка converge (`last_applied` = `last_acked`) проходит во всех
  тестах;
- в `replica-fb-stop` отставание applied появляется только пока Firebird
  реплики остановлен.

Пока этого прогона нет, N-09 на реальном кластере подтверждён только
частично: замеры и история работают, сравнение мастера с репликой — нет.
