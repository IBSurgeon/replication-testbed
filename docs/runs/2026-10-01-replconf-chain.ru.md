# Цепочка goafts → fbagent → node.json на HQbird 2.5/3.0: прогон 2026-10-01

Итог: **цепочка работает** на HQbird 2.5.9 и 3.0.15 после трёх правок
fbagent, найденных этим прогоном (разд. 5). Критерии 1–4 задачи
(hqcluster-node `docs/fbagent-replconf-valid-till-task.md`) выполнены на
новых сборках. Без правок выпуск (fbagent 2.55.3) на 2.5/3.0 не управляет
replconf совсем. Открыты три вопроса (разд. 6), один из них — падение
Firebird 3.0 на реплике при применении сегментов.

## 1. Сценарий

1. **Установка с нуля, выпуск.** Дроплеты без ничего. Скрипты fbagent
   `ops/linux-install/fbagent-fb30_known.sh` и `fbagent-fb25_known.sh`
   (`--enroll --cluster`, канал `stable`): Firebird HQbird + fbagent 2.55.3.
   Затем в goafts — кластер `managed` с датой `replconf_valid_till`. Узел
   2027.4.2 и RCM 2027.4.2 агент ставит сам из `stable`.
2. **Обновление на той же установке.** Агенты переведены в канал `ops-test`
   (`goafts.auto_update.channel`, `hqclusternode.update.channel`,
   `hqbirdrcm.update.channel`, перезапуск агента). Агент, узел и RCM
   обновились сами.
3. **Проверки цепочки** (разд. 4), репликация (база на мастере, reinit на
   реплику, запись на мастере → чтение на реплике).

весь прогон — через chess1 (решение владельца).

## 5. Найдено и исправлено (fbagent, не закоммичено)

1. **`replication_conf` для 2.5/3.0.** Блок `firebird` в `node.json` всегда
   называл `<root>/replication.conf`. HQbird 2.5/3.0 его не читают, и узел
   с таким значением не ведёт replconf (`not_replconf`,
   `config_backend_mismatch`): ни репликации, ни даты. Правка: при
   `firebird.version_line` 2.5/3.0 значение пустое (узел берёт свой файл);
   без версии 2.5 узнаётся по `aliases.conf` без `plugins.conf`. В
   существующем `node.json` убирается только путь, который агент записал
   сам.
2. **Версия HQbird 2.5 не найдена.** На 2.5, поставленном
   `ops/linux-install`, агент оставил `firebird.version: Unknown`. Для блока
   `firebird` это закрыто правилом п. 1; само определение версии не
   исправлено.
3. **Назначение после обновления агента.** Агент хранит назначение в
   `cluster/state.json` и спрашивает с ETag; goafts отвечает 304, пока не
   изменится ревизия. Старый агент сохранил назначение без новых полей, и
   дата не приходила. Правка: первый запрос после старта — без ETag.
   Подтверждено на стенде: дата пришла при старте новой сборки, без правок
   кластера.

Тесты: `internal/nodecontract`, `internal/clusterprov` (новые случаи на
каждую правку; тест п. 3 падает без правки).

## 6. Открыто

1. **Активация replconf не проходит.** Узел, поставленный агентом, работает
   от `firebird` и не может записать плагин в `<root>/plugins` и
   `replconf.properties` в `<root>/bin` (`permission denied`). На стенде:
   временные права группе `firebird` на время активации, потом `root:root
   0755`. Нужно решение: кто ставит плагин и `replconf.properties` (агент
   от root, установщик Firebird или узел через помощника агента).
2. **Узел не активирует replconf сам** на хосте без плагина HQbird: движок
   не «сломан», поэтому автоактивация (Р-С2) не срабатывает, и репликация
   не настроена, пока оператор не вызовет активацию.
3. **Firebird 3.0 на реплике падает при применении сегмента.** С 20:45 UTC
   каждый применённый сегмент на реплике c30: в `firebird.log`
   `pthread_mutex_unlock failed. Error code 1`, затем `terminated
   abnormally`; fbguard поднимает сервер, данные доходят, узел видит
   `IN_SYNC`. Первое применение после активации (20:27) прошло без сбоя.
   Сбой остаётся после перезапуска Firebird, нового reinit и любой даты
   (2027-06-15, 2027-06-30). Движок не обновлялся. На 2.5 и на мастере 3.0
   сбоев нет.

   **Причина: ошибка движка HQbird 3.0**, её включают trace-сессии fbagent.
   Узел, плагин replconf, fblwmon и `libcluster.so` ни при чём (найдено
   2026-10-01, воспроизведено и разобрано по дампу 2026-10-02).

   - **Условие.** Сбой бывает, если пользовательская trace-сессия появилась
     после того, как поток репликации реплики подключился к базе. fbagent
     запускает две сессии (задачи `trace_monitor` и
     `trace_monitor_conflicts`) примерно через 30 с после старта Firebird.
     Сегмент, применённый сразу при старте, проходит; следующий роняет
     сервер. Поэтому первое применение (20:25, при старте) прошло, а
     следующий сегмент пришёл только в 20:45. Мастер сегменты не применяет.
   - **Проверки на стенде c30**, по одному изменению:

     | Изменение | Сбой |
     |---|---|
     | Как было | да |
     | fbagent остановлен, трасс нет (2 сегмента) | нет |
     | Только сессия `trace_conflict.conf` | да |
     | Только сессия `trace.conf` | да |
     | `MonitoringPlugin = fblwmon` выключен, трасса есть | да |
     | Трасса только для `security3.fdb` | да |
     | fbagent работает, обе задачи трасс `enabled: false` | нет |

     `libcluster.so` в процесс Firebird не загружается.
   - **Воспроизведение.** Новый стенд test bed: мастер и реплика HQbird
     3.0.15.33885 (`fb_hqbird-30.sh`), дроплеты 4 ГБ, узел из
     `state/dist-rcdate`, плагин replconf 2.1.0, fbagent с задачами трасс по
     умолчанию. Нагрузка — один insert в одну таблицу раз в 2 с. Сегмент
     при старте применился, следующий (через ~20 с после запуска трасс
     fbagent) уронил Firebird. Дамп записал apport, стек снят gdb с
     debuginfo сборки `3.0.15.33885-HQbird-8962ddc`. Build-id в ELF нет:
     debuginfo подобран по CRC в `.gnu_debuglink`, совпали все пять файлов.
   - **Стек** (поток репликации, `ReplServer.cpp`):

     ```
     #5-7   system_call_failed ← Mutex::leave        pthread_mutex_unlock, EPERM
     #8-9   StableAttachmentPart::Sync::leave ← EngineCheckout
     #10    TraceManager::update_session           TraceManager.cpp:289
     #11-12 TraceManager::update_sessions ← needs
     #13    TRA_start                              tra.cpp:1716
     #14    ReplicationSlave::startTransaction     Replication.cpp:2227
     #15-20 REPL_replicate ← JAttachment::replicate ← fb_replicate
     #21-23 replicate ← process_archive ← process_thread   ReplServer.cpp
     ```

   - **Механизм по дампу.** `ReplicationSlave::startTransaction`
     (Replication.cpp:1186) отпускает mutex attachment, который вызвал
     `fb_replicate` (ATT_44), и берёт mutex внутреннего attachment реплики.
     TraceManager внутреннего attachment указывает на ATT_44. Новая
     trace-сессия (в дампе `FBAgent-…-conflicts`) заставляет его в
     `update_session` второй раз отпустить mutex ATT_44. У mutex нет
     владельца (`__owner = 0`), `pthread_mutex_unlock` возвращает EPERM, и
     при `BugCheckAbort = 1` сервер вызывает abort.
   - **Свежая сборка** `3.0.15.33885-HQbird-03e5152` (2026-10-02, отличается
     только `libEngine12.so`): тот же стек, сбой остаётся.
   - **Обход:** на реплике HQbird 3.0 выключить задачи fbagent
     `trace_monitor` и `trace_monitor_conflicts` в `agent_config.json`.
     Проверено с работающим агентом: сегменты применяются, PID Firebird не
     меняется. Не проверено, включат ли их снова сторож агента или goafts.
   - **Нужно:** исправление в движке HQbird 3.0 (дамп и стек — разработчикам
     движка); до него fbagent не должен запускать трассы на реплике HQbird
     3.0.
   - Каждый сбой пишет core 650–700 МБ в `/var/lib/apport/coredump` (apport
     хранит последние 5); первый сбой ещё ~2 мин пишет отчёт в
     `/var/crash`. Дамп, стеки и журналы — у оператора в
     `state/x30/crash1` (не в репозитории).
4. **cc2 и сеть** (разд. 2): большие загрузки к DO и Hetzner обрываются.
