Подробно:

- **`guidpromote` (3.0).** Тот же шаг `new_guid` на HQbird 3.0 через работающий

  у работающей реплики FB5 — алерт и `NEEDS_REINIT` (см. п. 4).
- **`tracegate` (3.0).** На реплике нет сессий трасс агента (агент пишет

- **HQbird 2.5 (дроплет).** `ops/linux-install` ставит 2.5 SuperClassic: в `bin`

  старте читает версию из `fb_smp_server -z` и пишет `2.5.9.x` и линию `2.5`.
  Загрузка fbagent с cc2 на дроплет DO не прошла (curl rc 28, известная
  проблема сети cc2–DO): агент поставлен из локальной сборки выпуска 2.58.0
  теми же шагами, что делает установщик.

## 4. Найдено и исправлено в ходе прогона

- **Узел: потерянный control file — это потеря данных.** После удаления
  `{source_guid}` у работающей реплики FB5 Firebird пишет «Database sequence has
  been changed from 0 to N, preparing for replication reset» и удаляет следующие
  сегменты без применения («is scanned, deleting»). Алерт
  `replica_control_missing` был warning; теперь critical, причина того же имени,
  `NEEDS_REINIT`, держится до reinit (узел `f55e272`, RCM `ecc7a08`, решение
  Р-G9 плана GUID).
- **fbagent: проверка трасс не видела реплику на стенде 3.0.** `node.json`
  узла, поставленного test bed, — `root:firebird 0600`, агент (firebird) его не
  читает; реплика падала под трассами агента. Второй признак: сторона реплики
  HQbird 3.0 пишет в `replication.log` «(slave)» — агент читает хвост журнала
  (fbagent `3870e20`). Покрывает и реплики без hqclusternode.
- **Test bed:**
  - `guidsigns` брал GUID мастера из `gstat` (`hostctl db-header`): на 2.5/3.0
    gstat печатает слова в другом порядке, чем узел. Эталон — API узла мастера;
  - `hostctl trace` не падает, когда сервер перезапускается (список пуст);
    `tracegate` считает непрочитанный список провалом;
  - `guidpromote` сравнивал GUID сегментов (порядок узла) с GUID из gstat
    (на 3.0 — другой порядок слов) и не находил сегменты нового мастера.
    Теперь сравниваются обе формы (`ops.guid_forms`).
